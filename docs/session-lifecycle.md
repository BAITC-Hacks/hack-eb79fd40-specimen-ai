# Жизненный цикл сессии

> Назначение: зафиксировать фактические состояния, переходы, сроки хранения и конкурентное поведение сессии пациента в реализации Demeu.

## Идентификаторы и владение

| Объект | Фактический формат и срок | Что даёт доступ |
|---|---|---|
| Ссылка врача | Первые 16 hex-символов UUID, TTL 7 суток | Позволяет создавать неограниченное число сессий до истечения TTL |
| Сессия пациента | Полный UUID, TTL активной сессии 1 час | Служит единственным bearer-секретом для chat и finalize |
| Завершённая сессия | Тот же UUID, хранение 24 часа | Позволяет повторно получить уже сохранённый результат через finalize |

Токен ссылки не одноразовый. Это **реализовано @ 19aa755** и расходится с текстом интерфейса «одна ссылка — один пациент». Отдельной аутентификации пациента или врача на этих маршрутах нет.

## Машина состояний

~~~mermaid
stateDiagram-v2
    [*] --> collecting: POST /api/chat/start
    collecting --> collecting: успешный POST /api/chat
    collecting --> finalizing: DONE-маркер / emergency / HARD_TURN_CAP / ручной finalize
    finalizing --> completed: анализ сохранён
    finalizing --> collecting: анализ завершился ошибкой
    collecting --> aborted: abortSession / истечение TTL после начала диалога
    collecting --> [*]: истечение TTL без хода пациента
    completed --> [*]: 24 часа после завершения
    aborted --> [*]: 24 часа после остановки
~~~

### Создание ссылки

POST /api/link создаёт запись doctor token со сроком жизни 7 суток. Маршрут не проверяет DOCTOR_ACCESS_CODE и не применяет rate limit. Один токен можно передавать в POST /api/chat/start многократно.

Якоря реализации:

- app/api/link/route.ts — HTTP-маршрут;
- lib/store.ts — createDoctorToken, isValidDoctorToken и очистка токенов.

### Старт сессии

POST /api/chat/start принимает token и необязательный language. После проверки токена стор создаёт сессию в состоянии collecting:

| Поле | Начальное значение |
|---|---|
| messages | Статическое приветствие assistant |
| turnCount | 0 |
| result | отсутствует |
| deliveryStatus | pending |
| createdAt | Текущее время; отдельного expiresAt нет |

Приветствие хранится для отображения, но lib/anamnesis.ts:toApiMessages отбрасывает всё до первого user-сообщения. Поэтому история, отправляемая Anthropic Messages API, начинается с user.

Если тело запроса не является JSON, текущий внешний catch возвращает 500 INTERNAL. Это **расхождение** с обычной классификацией ошибок клиента как 400 BAD_REQUEST.

### Обычный ход

Успешный POST /api/chat проходит такую последовательность:

1. Проверяет sessionId, сообщение и состояние collecting.
2. Вызывает диалоговый LLM с уже сохранённой историей плюс новым сообщением-кандидатом.
3. До append вычисляет forcedByRule и достижение HARD_TURN_CAP по кандидатной истории и следующему номеру хода.
4. Только после успешного ответа сохраняет user-сообщение; appendMessage увеличивает turnCount.
5. Сохраняет assistant-сообщение; оно счётчик не увеличивает.
6. После сохранения обоих сообщений принимает решение о финализации по заранее вычисленным forcedByRule/cap и DONE-маркеру либо возвращает обычный ответ.

Если диалоговый вызов LLM упал, сообщение-кандидат не сохраняется. Если добавление ответа assistant не удалось, сессия переводится в aborted.

**Ограничение emergency-пути:** regex-проверка выполняется после ответа диалогового LLM. При недоступности этого вызова потенциально экстренный текст пациента не сохраняется, не финализируется и не отправляется врачу.

Якоря реализации:

- app/api/chat/handler.ts — порядок одного хода и HTTP-ошибки;
- lib/store.ts:appendMessage — неизменяемое обновление и счётчик;
- lib/anamnesis.ts — диалоговый вызов и DONE-маркер;
- lib/redflags.ts:detectRedFlags — проверка реплик user.

## Счётчики и границы

| Ограничение | Реализовано @ 19aa755 |
|---|---|
| SOFT_TURN_CAP | 16; константа существует, отдельного перехода или UX-поведения нет |
| HARD_TURN_CAP | 20 успешных user-ходов; запускает автофинализацию |
| turnsLeft | max(0, 20 − turnCount) |
| Размер сообщения | После trim: 1–2000 символов |

Достижение HARD_TURN_CAP возвращает 200 с done: true и result, а не 429. Новый ход в completed возвращает 409 SESSION_COMPLETED.

## Единая финализация

Ручной POST /api/chat/finalize, DONE-маркер, emergency и turn cap сходятся в finalizeSession. Для одного sessionId параллельные вызовы финализации объединяются в один Promise.

~~~text
collecting
  → analysis in flight
  → store.completeSession(result)
  → HTTP 200
  → фоновая доставка Telegram/PDF
~~~

Свойства финализатора:

| Сценарий | Результат |
|---|---|
| Первый успешный вызов | Анализируется транскрипт, результат сохраняется |
| Повтор для completed | Сохранённый result, replayed: true, без повторного LLM и доставки |
| Вызов для aborted | 409 SESSION_COMPLETED |
| Нет ни одного user-сообщения | 400 BAD_REQUEST, анализ не запускается |
| Ошибка анализа | Сессия остаётся collecting и может быть повторена |

Доставка начинается после сохранения результата и не блокирует HTTP-ответ. Поэтому экран пациента не знает, дошло ли сообщение до Telegram, хотя текущая копия интерфейса сообщает об отправке.

Якоря реализации:

- lib/finalize.ts:finalizeSession — single-flight, анализ, сохранение, фоновая доставка;
- app/api/chat/finalize/route.ts — ручной маршрут и replay;
- lib/triage.ts:analyze — аналитический конвейер;
- lib/telegram.ts — уведомление и статусы доставки.

## Завершение, остановка и доставка

| Состояние | Можно писать в chat | finalize | Уведомление |
|---|---:|---:|---|
| collecting | Да | Запускает анализ | После успешного анализа |
| completed | Нет, 409 | Возвращает replay | Повторно не отправляет |
| aborted | Нет, 409 | 409 | Короткое уведомление только если был user-ход |

abortSession формирует короткое служебное уведомление без TriageResult. Оно включает идентификаторы сессии и ссылки, время и причину остановки. При нулевом числе ходов истёкшая сессия удаляется без уведомления.

deliveryStatus имеет состояния pending, sent и failed. sent означает успешную доставку всех обязательных текстовых частей всем настроенным адресатам; PDF может при этом не дойти. failed допускает частичную доставку. Очереди повторов нет.

## TTL и очистка

Стор находится только в памяти процесса.

| Объект | TTL / интервал | После истечения |
|---|---|---|
| Doctor token | 7 суток | Токен и связанные с ним сессии удаляются |
| Активная сессия | 1 час от createdAt, TTL не продлевается ходами | Нулевая удаляется; начатая переводится в aborted и уведомляет врача |
| completed / aborted | 24 часа | Удаляется |
| Sweep | Каждые 5 минут | Пакетно применяет правила выше |

Перезапуск процесса стирает токены, активные сессии, результаты, статусы доставки и single-flight-карту. Это допустимая для прототипа реализация SessionStore, но не долговременное хранение.

## Конкурентность и восстановление

| Вопрос | Фактическое поведение |
|---|---|
| Два finalize одновременно | Коалесцируются для одного sessionId |
| Два chat одновременно | Пер-сессионного mutex нет; ответы и turnCount могут гоняться |
| Обновление страницы | Нет GET-маршрута восстановления истории |
| Закрытие вкладки | Browser unload не вызывает abortSession |
| Перезапуск сервера | Сессия не восстанавливается |

Цель SPINE требует идемпотентную финализацию и стор за интерфейсом — это реализовано. Последовательная обработка конкурентных chat-ходов и durable recovery не реализованы и должны считаться отдельными эксплуатационными ограничениями.
