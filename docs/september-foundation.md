## Создание ссылки

`POST /api/link` сохраняет `200 { token }` и игнорирует тело запроса.

- При непустом `DOCTOR_ACCESS_CODE` требуется совпадающий `x-doctor-code`; иначе `401 { error, code: "UNAUTHORIZED" }`. Используется `timingSafeEqual` для буферов одинаковой длины.
- Без настроенного кода создание ссылки остаётся открытым для локальной разработки.
- Лимитер расходует попытку до проверки кода: неуспешная авторизация также ограничена. На IP используется ведро ёмкостью 10 запросов с пополнением 10 токенов в минуту.
- Если токена нет, ответ — `429 { error, code: "RATE_LIMITED", retry_after_ms }` и `Retry-After` в секундах, округлённых вверх. Стор не вызывается.
- Число активных ключей ограничено, устаревшие удаляются. При заполнении памяти новый ключ получает отказ; действующее ограничение не сбрасывается вытеснением.
- Сбой стора возвращает `500 { error, code: "INTERNAL" }` без внутренних деталей.

Ключ — IP из первого элемента `X-Forwarded-For`; отсутствующий или некорректный первый элемент использует общее ведро `unknown`. IPv6 нормализуется. Это требует доверенного reverse proxy, заменяющего клиентский заголовок. Репозиторные compose-файлы ограничивают публикацию приложения loopback либо внутренней сетью. Nginx-шаблон исправлен на `proxy_set_header X-Forwarded-For $remote_addr;`: сохранение клиентского первого элемента через `$proxy_add_x_forwarded_for` позволяло обходить лимит. Внешняя установленная proxy-конфигурация не проверена; шаблон ещё не применён на VPS.

Изменён только лимит `/api/link`. Другие маршруты и обработка provider 429 сохраняют прежние ограничения. Ведра локальны процессу и сбрасываются при рестарте; это не общий лимит нескольких экземпляров и не многопользовательская авторизация.

## Давняя история симптома

Уточнено правило `chest_pain`: исключается только отдельное последнее сообщение пациента, целиком описывающее явно завершённый эпизод годами назад. Примеры: «болело в груди год назад, прошло», «Боль в груди была пять лет назад, сейчас ничего не беспокоит».

Любой содержательный префикс, продолжение или следующая реплика пациента сохраняют прежнюю осторожную обработку. Поэтому текущий повтор, включая «Но сегодня это началось» без повторного названия симптома, не теряет emergency-сигнал. Свежие и неоднозначные эпизоды, дни/месяцы назад и короткие подтверждения не получают нового исключения. Это узкая текстовая эвристика, а не клинический порог. Роли, дословные цитаты, индексы и путь `rules_only` сохраняются; границы проверяются в `tests/unit/redflags.history.test.ts`.

## Воспроизводимость eval

`report.commit` описывает HEAD при первоначальной генерации отчёта, а не deployment и не чистоту worktree. Незакоммиченные исходники фиксируются хешами содержимого.

`--check` сохраняет записанный commit при сравнении с новым вычислением. Остальные поля, результаты кейсов, метрики и Markdown должны совпасть. Некорректный commit отвергается. Смена HEAD из-за документационного или report-only коммита сама по себе не делает расчёт устаревшим.

`provenance` и `readme_guard.required_hashes` аддитивно расширены ключами `runtime:<relative-path>`: транзитивные локальные импорты evaluator, включая типы/JSON, `package.json`, lockfile и `tsconfig.json`. Хеши включены в `run_id`; валидатор требует полный актуальный набор. `schema_version` остаётся 1, `TriageResult` не меняется. Абсолютный путь worktree и сгенерированный отчёт не входят в собственное вычисление хеша.

```bash
npm run eval -- --no-llm --allow-unvalidated
npm run eval -- --no-llm --allow-unvalidated --check
```

Первая команда регенерирует артефакты, вторая только проверяет. Режим остаётся `no-llm`, ограничения валидации и публикации метрик сохраняются. Это не измерение качества живого диалога.

## Локальные данные для проверок

Parity проверяет хеши исходной `data/raw/release_test_patients.csv` и спецификации `data/processed/feature_spec.json`; для нового worktree подключены уже имеющиеся файлы из рабочего дерева `gate0` ссылками внутри игнорируемых `data/raw/` и `data/processed/`. Отсутствие этих файлов по-прежнему не превращается в зелёный parity.

`tests/unit/live-scenario1-artifact.test.ts` проверяет необязательный локальный отчёт `reports/live-e2e/scenario1-structured-telegram.json`. Если файла нет, четыре проверки явно пропускаются. Если файл есть, все прежние проверки выполняются; повреждённый отчёт не принимается. Пропуск не означает успешную живую доставку. Тесты транспорта и генерации артефактов на синтетических данных выполняются отдельно.

## Согласованная граница следующего этапа

13.09 пользователь выбрал подтверждение внешних этапов врачом с историей изменений. Неизвестные очередь, дата госпитализации и явка остаются пустыми. Рекомендация модели не означает выполненное действие врача.

Для нового домена требуется отдельное дополнение SPINE: направление и события не заменяют `Session.status`; подтверждение хранит автора, время события, время записи и источник. Комплектность и отправка — разные факты. Постоянное хранение и серверная принадлежность данных врачу нужны до использования персонального потока. Эти новые сущности данной веткой ещё не реализованы.

Данные организаторов, новый полный PRD/ТЗ и нормативный справочник не появились в репозитории. Готовность D1/D2/B3/D4 к обучению требует аудита фактических данных.
