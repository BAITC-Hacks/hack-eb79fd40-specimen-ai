Это описание реализации, а не заявление о соответствии требованиям ИБ или законодательства. Непроверенные эксплуатационные свойства помечены явно.

## Краткая модель угроз

| Актив | Основная граница | Фактическая защита |
|---|---|---|
| Персональная ссылка | Браузер ↔ публичный API | 16 hex-символов, TTL 7 суток |
| История пациента | Браузер ↔ сервер ↔ Anthropic | UUID сессии как bearer-секрет; TLS зависит от деплоя |
| Результат триажа | Сервер ↔ браузер / Telegram | UUID сессии и Telegram credentials |
| Deep health probe | Мониторинг ↔ /api/healthz | Commit-bound HMAC |
| Telegram credentials | Сервер ↔ Telegram Bot API | Переменные окружения |
| Данные модели и маршрутизации | Файлы образа | Локальные JSON-артефакты; таблица маршрутизации не валидирована врачами |

Система не ставит диагноз: она формирует предварительную гипотезу, срочность и маршрутизацию, а решение принимает врач.

## Границы потока данных

~~~mermaid
flowchart LR
    P[Браузер пациента] -->|полный текст диалога| A[Next.js API]
    A -->|история и structured extraction| C[Anthropic API]
    A -->|полный TriageResult| P
    A -->|сводка и PDF с полным транскриптом| T[Telegram Bot API]
    T --> D1[Основной адресат]
    T --> D2[Дополнительные адресаты]
    A -->|in-memory до TTL или рестарта| M[SessionStore]
~~~

### Куда попадают данные пациента

| Получатель / место | Какие данные | Срок / контроль |
|---|---|---|
| Browser memory | Сообщения, sessionId, полный TriageResult после завершения | До закрытия/перезагрузки; durable storage не используется |
| In-memory SessionStore | Полный транскрипт, результат, токены и статус доставки | Активная сессия 1 час; terminal 24 часа; рестарт стирает |
| Anthropic | Полная доступная история для диалога; затем транскрипт для structured extraction | Политика внешнего провайдера; в репозитории срок не задан |
| Telegram | Текстовая сводка; PDF содержит полный транскрипт; всем настроенным chat ID | Политика Telegram и настройки получателей |
| Логи приложения | Служебные ошибки и идентификаторы без намеренного логирования текста | Логи reverse proxy и URL с токенами не проверены |

**Расхождение UI:** пациенту сообщается, что ответы увидит только врач. Реально текст обрабатывает Anthropic, а сводка и полный PDF-транскрипт могут уйти нескольким Telegram-получателям. Формулировку согласия нельзя считать точным описанием потока данных.

## Аутентификация и авторизация

### Публичные маршруты

| Маршрут | Реализовано @ 19aa755 |
|---|---|
| POST /api/link | Без аутентификации; x-doctor-code игнорируется |
| POST /api/chat/start | Проверяется только bearer-like doctor token в JSON |
| POST /api/chat | Проверяется только знание session UUID |
| POST /api/chat/finalize | Проверяется только знание session UUID |
| GET /api/healthz | Публичный shallow health |

DOCTOR_ACCESS_CODE объявлен в конфигурации и отправляется frontend при наличии, но серверный маршрут его не читает. Это прямое **расхождение** с README/SPINE, где описан опциональный код и 401.

Ни один app/api-маршрут не применяет rate limiter. Внешний 429 Anthropic обрабатывается как внутренняя повторная попытка и при исчерпании превращается в 500 LLM_UNAVAILABLE; публичного 429 и Retry-After нет.

### Ссылки и UUID как секреты

- Токен ссылки содержит 60 случайных бит: из 16 отображаемых hex-символов один nibble фиксирован версией UUIDv4. Он живёт 7 суток и не погашается после старта.
- Один токен создаёт неограниченное число сессий до истечения.
- sessionId — полный UUID и единственное право читать сохранённый результат через повторный finalize.
- GET-маршрута истории нет, но полный результат доступен обладателю sessionId через finalize.
- Передача токена в URL делает его доступным browser history, referrer-политике и access-логам reverse proxy; фактическая конфигурация этих логов **не проверена**.

### Deep health HMAC

GET /api/healthz?probe=extract использует отдельную защиту:

1. Клиент вычисляет HMAC из commit SHA и секрета.
2. Передаёт доказательство в x-demeu-health-proof.
3. Сервер сравнивает его безопасным сравнением.
4. Отсутствующий ключ, неверное доказательство и неавторизованный запрос получают одинаковый shallow 200-body с HTTP 404 и без обращения к провайдеру.

Авторизованный probe делает одну structured extraction без повторов, кешируется на время жизни процесса и объединяет параллельные запросы. Сам shallow health сообщает лишь наличие ANTHROPIC_API_KEY, а не доступность Anthropic.

Якоря реализации:

- app/api/healthz/route.ts — маршрутизация и маскировка;
- lib/health-deep.ts — HMAC, cache и single-flight;
- deploy/smoke-scenarios.sh — генерация proof без вывода секрета.

## Секреты и конфигурация

Допустимые безопасные обозначения в документации:

~~~dotenv
ANTHROPIC_API_KEY=<set-in-runtime-secret-store>
TELEGRAM_BOT_TOKEN=<set-in-runtime-secret-store>
TELEGRAM_DOCTOR_CHAT_IDS=<signed-int64>[,<signed-int64>...]
DOCTOR_ACCESS_CODE=<currently-unused>
APP_BASE_URL=https://<public-host>
COMMIT_SHA=<deployed-git-sha>
~~~

Нельзя добавлять реальные значения в Git, логи, тестовые фикстуры или скриншоты. .env игнорируется; .env.example должен содержать только имена и безопасные placeholders.

TELEGRAM_DOCTOR_CHAT_IDS — основной множественный параметр; legacy TELEGRAM_DOCTOR_CHAT_ID используется только как fallback. ID нормализуются, проверяются как ненулевые signed 64-bit integers и дедуплицируются с сохранением порядка.

## Минимизация и разглашение

| Область | Реализовано @ 19aa755 | Риск / цель |
|---|---|---|
| Anthropic input | Полный диалог нужен двум LLM-этапам | Нет отдельной редактуры PII |
| Telegram text | Клиническая сводка частями до 4096 символов | Может уйти нескольким получателям |
| Telegram PDF | Полный транскрипт и результат | Более широкий объём, best-effort |
| Browser response | Полный result возвращается физически | DoctorPanel скрыт по умолчанию, но данные уже в клиенте |
| Abort notice | sessionId, doctorToken, время, причина | Идентификаторы попадают в Telegram |
| Routing data | validated: false | Нельзя заявлять клинически подтверждённые метрики маршрутизации |

Обязательная отрицательная оговорка «это не диагноз, решает врач» добавляется к каждой обязательной текстовой части Telegram. Она не заменяет контроль доступа, согласие или врачебную проверку.

## Доставка и частичные отказы

Доставка Telegram/PDF асинхронна относительно HTTP-финализации:

- сервер сначала сохраняет result и отвечает браузеру;
- текст отправляется всем настроенным получателям и всеми частями даже после отдельных ошибок;
- PDF создаётся один раз и отправляется каждому получателю best-effort;
- sent означает успех обязательного текста всем адресатам, но не гарантирует PDF;
- failed может означать частичную доставку;
- постоянной очереди и автоматических повторов нет;
- replay финализации не инициирует повторную отправку.

Поэтому сообщение UI «сводка отправлена» появляется раньше, чем известен deliveryStatus. Browser API не предоставляет статус доставки.

## Клинические защитные свойства

| Свойство | Реализовано @ 19aa755 | Ограничение |
|---|---|---|
| Emergency rules dominate | Любой emergency red flag устанавливает emergency независимо от модели | Regex-покрытие реальной речи требует клинической валидации |
| Проверяемая цитата | Quote является подстрокой индексированной user-реплики | Проверяемость не доказывает правильность интерпретации |
| Отрицания | Обрабатываются отдельными негативными шаблонами | Естественный язык шире набора фикстур |
| Источник assistant исключён | Regex сканирует только role=user | Emergency-проверка идёт после диалогового LLM |
| Structured validation | Некорректный JSON/контракт ведёт к rules_only | rules_only не имеет извлечённого анамнеза |
| Human-in-the-loop | Disclaimer и clinician-facing summary | Технического подтверждения врачом в продукте нет |

Маршрутизация использует data/pathology_map.json с validated: false. До врачебной валидации метрики urgency/routing должны сопровождаться этой оговоркой.

## Frontend и согласие

Фактические несоответствия:

| UI-текст / поведение | Реальность |
|---|---|
| «Одна ссылка — один пациент» | Ссылка переиспользуется 7 суток |
| Поле кода доступа появляется после 401 | Backend никогда не выдаёт предусмотренный 401 |
| «Ответы увидит только врач» | Anthropic обрабатывает текст; Telegram может иметь несколько адресатов |
| «Сводка отправлена» | Доставка ещё идёт в фоне и может частично упасть |
| Result скрыт без demo=1 | Полный объект всё равно получен браузером |

Языки интерфейса ru/kk не означают подтверждённую эквивалентность аналитики: structured extraction и clinician summary ориентированы на русский; полноценное качество казахского пути **не проверено**.

## Рекомендованный порядок снижения риска

Это список целей, а не описание готового функционала:

1. Закрыть POST /api/link фактической проверкой кода врача и синхронизировать контракт 401.
2. Добавить rate limit по IP и токену с корректным 429/Retry-After.
3. Сделать персональные ссылки одноразовыми либо честно изменить UI.
4. Перенести emergency regex до диалогового LLM и сохранить безопасный путь уведомления при отказе провайдера.
5. Не возвращать clinician-only поля в браузер пациента.
6. Исправить согласие с перечислением Anthropic, Telegram, получателей, сроков и полного PDF-транскрипта.
7. Добавить durable очередь доставки, наблюдаемый status endpoint и безопасные повторы.
8. Включить редактирование access-логов и строгую Referrer-Policy.
9. Провести врачебную валидацию pathology_map до заявлений о качестве маршрутизации.

## Проверка перед публикацией

- В документах и примерах нет реальных ключей, chat ID и session UUID.
- grep истории не находит Anthropic/Telegram credentials.
- Reverse proxy не пишет query/path tokens целиком — **не проверено** до аудита VPS.
- Адресаты Telegram сверены с ожидаемым списком.
- Deep probe HMAC не выводится в CI-лог.
- Формулировка согласия совпадает с фактическими получателями данных.
- Routing table явно помечена validated: false.
