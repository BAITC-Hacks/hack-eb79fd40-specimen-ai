# Сентябрьское дополнение к SPINE: наблюдаемые направления

Статус: техническое дополнение для новых задач, не замена июльского SPINE. Авторизация разработки — пользователь 13.09.2026; внешние сведения подтверждает врач, неизвестные остаются пустыми. Контракты `SessionStore`, `Session.status`, `TriageResult`, ML и существующих ответов опроса не переопределяются.

## Хранилище

Опциональный файловый adapter выбирается явным `DEMEU_DATA_DIR`, иначе старый memory режим. Один процесс и локальная файловая система, не NFS/cluster. Записи сериализованы, detached candidate становится видимым только после durable commit; неисправный/неизвестный snapshot не заменяется пустым. Сессии сохраняют июльский TTL. Направления и события хранятся отдельно и не удаляются по TTL токена/сессии. Production-включение персонального потока требует отдельного утверждения условий хранения и доступа; эта итерация не вводит бессрочный медицинский архив и не выполняет rollout.

## Личность и права

Учетные записи назначаются оператором на сервере: id, displayName, role owner/doctor/analyst, organizationId, password hash, sessionVersion, необязательный личный Telegram chatId. Никакой публичной регистрации или назначения ролей из браузера. Подписанная HttpOnly cookie содержит id/expiry/version, актуальные права проверяются сервером. Нет настроек/секрета — workspace недоступен; общий DOCTOR_ACCESS_CODE не обходит workspace auth. Изменения требуют same-origin проверки, все персональные ответы no-store.

Doctor видит и изменяет только свои записи; owner — записи пространства; analyst получает только отдельный агрегатный DTO без id сессии/ссылки/направления, меток пациента и текстов. Чужая детальная запись неотличима от неизвестной. Непривязанные старые сессии не присваиваются вошедшему автоматически.

## Отдельный домен

Направление содержит устойчивого владельца/организацию, минимальную метку эпизода (ФИО/ИИН не требуются), профиль и организацию назначения, ссылку на собственный опрос при наличии, разрешённый снимок результата без транскрипта, ревизию и историю. Одному человеку допустимо несколько направлений; глобальный реестр пациентов не вводится.

Подтверждения независимы: queue = true/false/null, scheduledDate = YYYY-MM-DD/null, attendance = attended/not_attended/null. Наступление даты не устанавливает явку. Отправка не вычисляется из комплектности. Известный поздний этап не требует выдумывать неизвестные ранние факты. Отмена, возврат и исправление требуют явного действия и причины.

Каждое изменение хранит автора с сервера, записанное сервером время, фактическое время события или null, source=doctor_confirmation, before/after, причину и revision. Данные и история записываются одной транзакцией. expectedRevision защищает от потери параллельных правок (409); повтор ключа идемпотентности с тем же содержимым не добавляет событие, с другим содержимым отклоняется.

## Новые поверхности API

Новые workspace/auth и referrals API — отдельное пространство, старые публичные API не расширяются выдачей персональных списков. Точные типы запросов/ответов фиксируются в модуле referrals до подключения UI. Маршруты: `/api/workspace/auth`, `/api/workspace/intakes`, `/api/referrals`, `/api/referrals/[id]`, `/api/referrals/[id]/events`, `/api/referrals/[id]/examinations`, `/api/referrals/[id]/patient-memo`, `/api/workspace/aggregates`. UI `/workspace` использует только эти серверные границы доступа. Клиентские owner/organization поля не источник полномочий.

### Агрегированные сведения о моделях

Сентябрьский слой добавляет три read-only операции: `/api/models`, `/api/models/benchmarks` и `/api/models/{id}`. Это аддитивное расширение канонического списка SPINE §3, а не изменение существующих маршрутов опроса, `TriageResult` или замороженного API `lib/model.ts`. Все три операции требуют действующую HttpOnly cookie рабочего пространства; owner, doctor и analyst получают один и тот же агрегированный DTO без персональных записей. Ответы имеют `Cache-Control: no-store`.

`GET /api/models` возвращает `{ schemaVersion: 1, models: ModelCard[] }`. Карточка содержит стабильный id, задачу, тип контура, доступность, состояние runtime, `researchOnly`, статус метрик, основную метрику, baseline, ограничения и `detailPath`. `GET /api/models/benchmarks` возвращает один замороженный red-flag benchmark правил, Qwen и Jev с корпусом, дизайном оценки и кандидатами. `GET /api/models/{id}` расширяет карточку allowlisted сведениями об источнике, оценке, конфигурации и причине недоступности.

Эти маршруты не запускают inference и не являются patient-level API. D1, B3, D2, Qwen и Jev остаются research-only, пока отдельно не выполнены продуктовая активация, runtime parity и необходимые проверки. Runtime LR описывается как активный только в своём существующем triage-контуре. Эндпоинты не возвращают predictions, веса, `feature_order`, `class_order`, сырые строки, внутренние категории сериализованной модели, секреты, абсолютные пути и скрытые врачебные материалы.

Значение `null` означает отсутствие честного измерения, а не нулевой результат. Jev измерен одним zero-shot research-only прогоном через alpha endpoint без seed: `question_spec_id=redflags-eight-trigger-v1`, запрошен `typesafe/jev-1.13`, provider вернул `typesafe/jev-1.13-20260917`. На замороженном корпусе из 160 случаев получены TP `79`, FP `0`, TN `80`, FN `1`, precision `1`, recall `0.9875`, F1 `0.9937106918238994` и false-positive rate `0`; recall RU `0.975`, KK `1`, `trigger:suicidal` — `1`. Единственный пропуск находится в `trigger:consciousness` (TP `9`, FN `1`, recall `0.9`); исходная фраза случая через API не публикуется. Точный текст Jev question не был сохранён отдельным версионированным артефактом: `question_spec_id` фиксирует семантику восьми групп, поэтому внешний вызов нельзя воспроизвести побайтно.

Jev обработал корпус 16 batch-запросами: total `3042 ms`, mean `190.125 ms`, p50 `182 ms`, p95 `260 ms`; `usage.cost` составил `0.001810746 USD`, input `43113`, output `3264` токена. Эти значения latency относятся к batch до 10 случаев и напрямую не сравнимы с per-item/per-request latency других кандидатов. Корпус, восьмигрупповая taxonomy, labels и threshold `0.5` одинаковы для сравнения, но правила дорабатывались на этом же корпусе и остаются in-sample, а Jev — одиночным zero-shot прогоном без seed. Jev не активирован в runtime, результат не является независимой клинической валидацией или доказательством безопасности.

Если будущий внешний кандидат недоступен, его `metrics`, `slices`, `latency` и `cost` остаются `null`, а причина доступна отдельно. Для D2 метрики остаются `null`, пока нет наблюдаемого лабораторного target. Для LR вместе с числами сохраняются `mode=no-llm` и ограничение непроверенной врачами таблицы маршрутизации. Research-only результаты правил явно не заявляют unseen generalization или клиническую валидацию.

Общие ошибки: `401 UNAUTHORIZED`, `503 WORKSPACE_UNAVAILABLE`, `503 MODEL_EVIDENCE_UNAVAILABLE`; detail дополнительно возвращает `404 NOT_FOUND` для неизвестного стабильного id. Повреждённый или неполный отчёт не отдаётся частично: слой модели доказательств закрывается fail-closed.

## Комплектность и агрегаты

Версионированный справочник обязан иметь источник, область действия и validated. Пока источник отсутствует, справочник unavailable, не пустой полный пакет. Неизвестная дата/годность или условие не превращается в готовность. Памятка — отдельный разрешённый DTO без анамнеза/гипотезы/транскрипта, не копия врачебного PDF.

Runtime-справочник `data/examination_requirements.json` имеет версию `2025-02-17-order-9-appendix-5`: восемь профилей госпитализации, общий блок из 13 позиций и профильные исследования. В развёрнутых профилях 148 строк, 57 уникальных кодов; сроки заданы у каждой позиции, где они есть в источнике. Источник — [редакция приложения 5 от 17.02.2025 № 9](https://www.adilet.zan.kz/rus/docs/V2500035735). Файл имеет `validated: false` до проверки врачом больницы. Направление хранит выбранный профиль и снимок версии перечня, чтобы последующая правка файла не переписывала уже проведённую проверку. Код МКБ-10 хранится отдельно для аналитики; комплектность берётся из профиля. Для старых направлений без снимка версия на момент создания неизвестна. Один исходный текст метки адаптирован к языковому ограничению проекта: «по основному заболеванию» вместо исходной формулировки.

`GET /api/reference/examination-requirements` — аддитивная read-only поверхность B1 к списку SPINE §3. Она требует действующую HttpOnly cookie рабочего пространства, разрешена owner, doctor и analyst, не принимает тело или query-параметры и всегда отвечает с `Cache-Control: no-store`. Ответ `{ schemaVersion, catalogue, summary, profiles }` публикует версию и источник, область действия, `validated`, `validationStatus`, все восемь профилей и контрольные числа `profileCount=8`, `requirementOccurrenceCount=148`, `uniqueRequirementCount=57`. Персональные записи, сведения учётной записи и секреты в DTO не входят.

У каждой позиции присутствуют `id`, `label`, `required`, `conditional` и `validForDays`. Значение `validForDays: null` означает только то, что нормативный источник не задал срок актуальности; это не ноль дней и не утверждение о бессрочности. Текущие `catalogue.id=b1-examination-requirements-v1`, `validated: false` и `validationStatus: unvalidated` нельзя скрывать или трактовать как одобрение врачом. Ошибки fail-closed: `400 BAD_REQUEST` для любой query-строки, `401 UNAUTHORIZED`, `405 METHOD_NOT_ALLOWED`, `503 WORKSPACE_UNAVAILABLE` и `503 REFERENCE_CATALOGUE_UNAVAILABLE` для повреждённого или неполного справочника.

Длительность наблюдаемого состояния и подтвержденное время внешнего события различаются. Неизвестные времена не считаются нулями. Настройка задержки — операционная, не медицинский норматив. Малые группы не раскрываются аналитику через произвольные фильтры; точные персональные сводки доступны только owner/doctor в их области. Прогнозы не выдаются без обученной проверенной модели.

## Telegram и рестарт

В workspace режиме обе доставки (completed/aborted) выбирают только владельца записи. Нет владельца/получателя — видимый отказ, никогда глобальная рассылка. Во время реализации внешние отправки проверяются через порты без сети. Сбой между внешней отправкой и локальным подтверждением неоднозначен: нельзя обещать exactly-once или незаметно повторять сообщение. Pending после рестарта требует отдельной проверки/явного повтора, не означает доставлено.

## Клиническая семантика опроса

Задача ClickUp A от 21.09.2026 вводит аддитивное уточнение старого контракта SPINE. Старые массивы анамнеза не различали явное отрицание и отсутствие ответа. Новые результаты содержат `history_status` со значениями `reported`, `denied`, `not_stated` для перенесённых состояний, хронических состояний, аллергий и лекарств, а также `negative_findings` для явно отрицаемых симптомов и функций. Старые snapshots и fixtures нормализуются: непустой массив означает `reported`, пустой массив без нового статуса означает `not_stated`; отрицание из пустоты не выводится. Вектор модели строится только из положительных признаков.

Это намеренное расхождение со старым SPINE: при воздержании модели языковой слой больше не формулирует гипотезу. Результат получает точный текст «Модель воздержалась — гипотеза не сформирована, решение за врачом.» и confidence `0`; жалоба пациента в этот текст не подставляется. Пациентские ответы о завершении и экстренной маршрутизации выбираются сервером и не содержат названий болезней.

## Режим обработки без внешней языковой модели

Задача ClickUp D от 21.09.2026 добавляет статический режим процесса `DEMEU_PROCESSING_MODE=external_llm|deterministic`; значение по умолчанию — `external_llm`, другое значение останавливает запуск с ошибкой конфигурации. Это аддитивное расхождение со старым SPINE, где был описан только внешний LLM-путь. В `deterministic` фиксированный русский или казахский опрос выбирает следующий вопрос только по сохранённой истории, а итоговый анамнез собирается локальными детерминированными правилами. До следующего вопроса всегда проверяются emergency-правила. Внешний chat turn, структурированное извлечение и обученная модель в этом режиме не вызываются; ключ Anthropic не требуется.

`TriageResult.processing_mode` — независимое необязательное поле для совместимости со старыми snapshots. `source` сохраняет прежнюю семантику: детерминированная сводка имеет `source=rules_only`. Без emergency или существующего контекстного правила приоритет равен `planned`. В этом режиме гипотеза не формируется; врач получает ответы фиксированного опроса и срабатывания правил безопасности без текста об ошибке извлечения. Health публикует точный `processing_mode`; deploy и deep-health пропускают Anthropic probe и проверку ключа в deterministic-режиме, но требуют provider-free deep self-test фиксированного опросника и трёх safety-сценариев, сохраняя commit/model/health/TLS/storage gates. Врачебные поверхности прямо сообщают, что ответы пациента не передавались внешней языковой модели. Они не утверждают, что все данные остаются локально: доставка врачу через Telegram остаётся отдельным каналом.
